# Packet Capture Analysis: Kerberos Authentication and LDAP Bind During gpupdate

## Objective
Capture and interpret the actual network traffic generated by a domain-
joined Windows 11 client authenticating to Active Directory, to build
packet-level literacy with Kerberos — the authentication protocol
underlying nearly all enterprise Windows authentication — rather than just
knowing the term.

## Setup
- **Capture point:** Windows 11 client (10.0.0.20), Wireshark + Npcap
- **Interface:** physical Ethernet adapter (not the loopback adapter, which
  shows unrelated local-process traffic)
- **Trigger:** `gpupdate /force`, run while capturing, to force the client
  to re-authenticate and re-pull Group Policy from the DC (10.0.0.10)
- **Filter applied post-capture:** `dns || kerberos`

## Walkthrough

The capture shows a complete, textbook Kerberos exchange, in order:

| # | Packet | What's happening |
|---|---|---|
| 1 | **AS-REQ** | Client requests a Ticket-Granting Ticket (TGT) from the DC — the first step of Kerberos authentication. |
| 2 | **KRB Error: KRB5KDC_ERR_PREAUTH_REQUIRED** | Not a failure. The DC is enforcing pre-authentication — the client must prove knowledge of the password (encrypted) before a TGT will be issued. This response is a normal, expected part of nearly every Kerberos exchange. |
| 3 | **AS-REQ (retry)** | Client resends the request, this time including encrypted pre-authentication data. |
| 4 | **AS-REP** | DC validates the pre-auth data and issues the TGT. |
| 5 | **TGS-REQ** | Client presents the TGT back to the DC, requesting a *second*, service-specific ticket — in this case, for LDAP. |
| 6 | **TGS-REP** | DC issues the LDAP service ticket. |
| 7 | **LDAP bindRequest ... sasl** | Client authenticates to LDAP using the ticket just obtained, via SASL. |
| 8 | **LDAP bindResponse ... success** | Bind succeeds — this is the actual mechanism `gpupdate` uses to pull Group Policy data from AD. |

This demonstrates Kerberos's core two-ticket design: one ticket (TGT) to
prove identity to the domain generally, and a separate, per-service ticket
(TGS) requested for each individual service the client needs to reach — a
client never hands its TGT directly to a service; it always exchanges it
for a service-specific ticket first.

## Key Evidence: Confirming the LDAP Bind Actually Used the Kerberos Ticket

Two things in the capture, together, prove the LDAP authentication was
Kerberos-based rather than just LDAP traffic coincidentally following
Kerberos traffic in time:

1. **The `bindRequest` Info column reads `"<ROOT>" sasl`** — SASL (Simple
   Authentication and Security Layer) is a pluggable auth framework; a
   plaintext username/password bind would not show `sasl` here at all.
2. **Expanding the LDAP layer on that packet shows the SASL Mechanism
   field set to GSS-SPNEGO/GSSAPI** — this is LDAP explicitly declaring
   it's authenticating via Kerberos, not a plaintext credential.

The sequencing (TGS-REQ/TGS-REP specifically naming the LDAP service,
immediately followed by an LDAP bind using that same auth mechanism) is
the causal link — not just two protocols appearing near each other in a
busy capture.

## Noise Observed and Correctly Ignored
Early in the capture, several DNS queries for `wpad.lab.local` returned
`No such name` (NXDOMAIN). This is unrelated to authentication — Windows
automatically checks for a Web Proxy Auto-Discovery server on every
network change, and correctly gets no answer since this lab doesn't run
one. Worth recognizing as expected background noise rather than a fault
to chase.

## What This Demonstrates
Reading raw Kerberos/LDAP traffic and correctly explaining *why* each
packet appears in the order it does — including recognizing an error
response (`KRB5KDC_ERR_PREAUTH_REQUIRED`) as expected protocol behavior
rather than a fault — is a foundational skill for SOC analyst and
detection engineering work. Real-world Kerberos-based attacks (e.g.,
Kerberoasting, AS-REP roasting, Golden/Silver Ticket attacks) are only
recognizable as *abnormal* traffic to someone who already knows what
*normal* Kerberos traffic looks like at the packet level.
